# DSH 内置浏览器：记录丢失诊断 + 插件调研

调研时间：2026-10-23 07:20–07:40（Asia/Singapore）
环境：DeepSeek Harness Desktop，profile `desktop`，插件 `dsh-browser-cdp@1.2.3`（npm latest 1.6.0）

---

## 一、结论先行

1. **“关掉 dsh 记录就没了”不是持久化没开，而是两个叠加故障**：
   - **A（致命，已修复）**：macOS 上 `~/.local/bin/google-chrome` 是**软链**，Chrome 主二进制用自身路径 `dlopen ../Frameworks/...`，软链导致路径解析错 → 进程 `Abort trap: 6` → **浏览器根本起不来**。所以你看到的“记录全没”首先是“浏览器从来没成功启动”。
   - **B（机制性，未修代码）**：Chrome 的 cookie **只在优雅关闭时落盘**。dsh 退出时如果浏览器被强杀，本次会话的登录态/新 cookie 全部丢失。
2. **磁盘持久化本身是好的**：profile 在 `~/.local/share/ego-lite-linux/profile`，实测重启后 cookie 存活（见 §3）。
3. **插件选型**：主力继续用 `dsh-browser-cdp`（唯一有实时观屏、登录导入、任务空间），想要更好 UI 可评估 `dsh-browser-plus`；想直接操控**你已登录的真实 Chrome**，`@caob23/dsh-browser-control` 是最成熟的一个（41 星）。**三选一，不要同时装**（工具名冲突）。

## 三、实测记录（可复现）

### 3.1 故障复现

```text
$ node bin/ego-browser.mjs  <<'JS'  ... page.goto(...)
ego: browser did not come up on display darwin-desktop; falling back to Xvfb
Error: browser failed to come up on display darwin-desktop:
       Chrome did not expose a DevTools port within 20000ms
```

手动用**软链**启动 Chrome：

```text
$ ~/.local/bin/google-chrome --user-data-dir=/tmp/egoC --remote-debugging-port=0
dlopen /Users/ruler/.local/bin/../Frameworks/Google Chrome Framework.framework/...: no such file
Abort trap: 6
```

同一条命令换成**真实路径**：正常，2 秒出 `DevToolsActivePort`。

### 3.2 已落地修复（最小可逆）

```sh
# 备份原软链（保留）
~/.local/bin/google-chrome.symlink-backup-20261023

# 新内容：exec 真实二进制
#!/bin/sh
exec "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" "$@"
```

回滚：`mv ~/.local/bin/google-chrome.symlink-backup-20261023 ~/.local/bin/google-chrome`

> 为什么改垫片而不是改插件配置：`runtime/ego-linux/src/chrome.mjs:161 resolveBinary()` 会走 `which()` 拿 PATH 上的 `google-chrome`，垫片对**所有**启动路径生效；插件设置里的 `chromePath` 作为第二道保险（见 §4）。

### 3.3 持久化验证

| 场景 | 结果 |
|---|---|
| 设 cookie → `Browser.close`（优雅）→ 重启 | ✅ cookie 还在 |
| 设 cookie → `kill -9` → 重启 | ❌ cookie 丢失（DB mtime 未变） |

`task-spaces.json` 在重启后保留（space 名 + urls 可用于重认领），但浏览器以 `--no-startup-window` 启动，**不会恢复上次的标签页**。

## 四、还需要你做的配置（按优先级）

| # | 动作 | 为什么 | 怎么做 |
|---|---|---|---|
| 1 | 设置里把 **Chrome 路径** 填绝对路径 | 独立于 PATH 垫片，插件重装/升级也不会退化 | 设置 → 插件 → dsh-browser-cdp → `chromePath` = `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome` |
| 2 | 打开 **idleTimeoutMin**（建议 10） | 空闲 10 分钟**优雅**停浏览器，cookie 有机会落盘，而不是等你退出 dsh 被强杀 | 同一设置卡，`idleTimeoutMin: 10` |
| 3 | 结束浏览前调 **`bcdp_auth_flush`** | 官方就是干这个的：“Chrome only flushes cookies to disk on graceful close, this nudges it to persist them now” | 让我在收尾时调用，或点观察窗“已登录，保存” |
| 4 | 需要长期登录态：**`bcdp_login_import`** | 从你的真实 Chrome 按域名导入 cookie，写进同一个 profile，重启永久保留 | `bcdp_login_import(dryRun=true)` 先看清单，再选域名导入 |
| 5 | 别开 **空间隔离**（`isolateSpaces`） | 开了就是内存沙盒，重启必清空。当前无显式配置=默认 `false`（磁盘 profile），保持即可 | 设置卡确认关闭 |
| 6 | 关注 **space 30 分钟空闲回收** | 默认 30 分钟没人用会自动关掉 space（标签一起没），容易被当成“记录被清” | `EGO_LINUX_SPACE_IDLE_MIN=0`（需在 dsh 启动环境里设，GUI 启动较麻烦，可选） |
| 7 | 升级 **1.2.3 → 1.6.0**（可选） | 工具面收敛：`bcdp_space(+op:open/close/list/handoff/takeover)`、新增 `bcdp_tab`、`bcdp_wait(+op)`；但**工具名变了**，旧习惯/脚本要改 | `dsh plugin --profile desktop add dsh-browser-cdp@1.6.0` |

### 选型建议（给“更好服务开发”）

- **保留 cdp 作为唯一浏览器**：它已经是 38 个工具、有观屏、有登录导入、有 Lightpanda 降级，生态里没有第二个覆盖这么全的。
- **UI 想升级**：先看 `dsh-browser-plus` 的截图再决定换不换。它是“真实桌面浏览器窗口 + 页面任务栏 + 操作轨迹”，比现在的右下角浮动球/侧边栏 Tab 更接近 Cursor 的体验。代价：换掉 cdp，`bcdp_*` 工具全变 `browser_*`，我这边的习惯/脚本要重建。
- **开发主战场在内网系统**（需要你已登录的账号）：`@caob23/dsh-browser-control` 是正解——扩展模式直接复用你的 Chrome 登录态，绕开“导入 cookie + 会过期”这条链路。
- **不要叠装两家**：都注册 `browser_*`/占浏览器单例，会互相抢。

### 7.3 两个必须说清的坑

1. **`idleTimeoutMin` 热改不生效，必须重启 dsh。**
   代码位置 `lib/index.js:7861`：`ctx.effect(() => { if (cfg.idleTimeoutMin <= 0) return; setInterval(...) })`。
   挂载时默认值是 0 → effect 直接 return，定时器根本没建。实测：改成 1、重新触发一次 `bcdp_*`、等 85s，浏览器**没停**。
   重启后生效；届时空闲 30 分钟走 `--stop`（优雅），会 flush。
2. **`idleTimeoutMin` 的代价**：到点会把浏览器连标签一起关掉（下次调用自动重启，但标签不恢复）。所以设 30 分钟而不是 10，且保留 `dsh-browser-stop` 作为手动/按需的提前优雅停。

## 八、dsh-browser-cdp vs dsh-browser-plus 对比（2026-10-23 08:00）

方法：读两边的 npm 包本体（不只是描述）。cdp 读已装的 `1.2.3` 源码 + README；plus 下载 `0.5.2` tarball 解包读 `package.json` / `host-main.js` / `README.md` / `CHANGELOG.md` / `docs/MIGRATION.md`。**两边都没跑起来对比**——plus 没装（装了会抢 `ctx.browser` seam）。

### 8.1 硬事实

| 维度 | dsh-browser-cdp 1.2.3（1.6.0 可升） | dsh-browser-plus 0.5.2 |
|---|---|---|
| 浏览器实体 | **你自己的系统 Chrome**（CDP 附着），另支持远程 CDP 端点 / Lightpanda | **自托管 Electron 44 窗口**（WebContentsView），与你的 Chrome 无关 |
| 额外下载 | 0（复用已装 Chrome） | **Electron 44.9.3（optionalDependency，约 200MB）** |
| 包体积 | 1.8MB / 57 文件 | 2.0MB / 91 文件（不含 Electron） |
| 工具面 | 38 个 `bcdp_*`（含 `bcdp_cli` 任意 heredoc、`bcdp_cdp` 原始 CDP、`bcdp_http`） | ~36–40 个 `browser_*`（含 `browser_execute`、`browser_scrape`、`browser_replay`） |
| 登录态来源 | 磁盘 profile + **`bcdp_login_import`（按域名从你的真实 Chrome 导 cookie）** | 独立 `$DSH_HOME/dsh-browser-plus-host` userData + `browser_auth` export/restore |
| 可见性 | 真实 Chrome 窗口 + 观察窗（SSE 推流，可点可输入） | **Electron `WebContentsView` 真窗口 + 常驻顶栏 + 任务面板 + 操作轨迹 + 悬浮球** |
| 多任务 | task spaces（标签集合），多 session 共用一套 | 每 session 隔离视图/标签/历史，后台任务不抢前台，缩略图按需刷新 |
| 人机协作 | 观察窗里手动点；「弹出窗口」换成有头窗口接管 | **显式接管/交还按钮 + `browser_handoff`** |
| 诊断能力 | `bcdp_cdp` 原始协议、`bcdp_cli` 任意脚本、`bcdp_wait_for_response` | `browser_console` / `browser_network`（各 200 条环形缓冲）、`browser_emulate`、`browser_pdf`、`browser_highlight` |
| 兼容声明 | `engines.dsh` 明确列出 `0.2.1-rc.2` ✅ | peer 写 `^0.2.0-rc.1`，**宿主是 0.2.1-rc.2（严格 semver 不匹配 prerelease）**，且无 `engines.dsh` 护栏 ⚠️ |
| 维护/热度 | 周下载 6,188，1.6.0（10-22） | 周下载 221，0.5.2（10-22），7★ |

### 8.2 分场景结论

| 你的诉求 | 更好的是 | 理由 |
|---|---|---|
| 「看的见 agent 在干什么」、任务流管理、随时接管 | **plus** | 真窗口 + 顶栏 + 任务面板 + 操作轨迹 + 悬浮球，这是 cdp 的观察窗给不了的 |
| 写代码/调接口/脚本化批处理 | **cdp** | `bcdp_cli` 能让 agent 直接跑多步 heredoc、`bcdp_cdp` 发任意协议、`bcdp_wait_for_response` 等响应 |
| 复用你已登录的账号（内网/SSO） | **cdp** | `bcdp_login_import` 按域名导入真实 Chrome cookie；plus 要手动 export/restore |
| 不想多装 200MB、想少一个进程 | **cdp** | plus 自带一套 Chromium |
| 多任务并行、后台任务不抢镜头 | **plus** | 每 session 隔离视图是它的核心设计 |
| 稳定性优先 | **cdp** | 下载量 28 倍、工具面被反复打磨；plus 0.5.x 仍在快速迭代（0.5.0→0.5.2 两周内） |

### 8.3 我的判断

**在你当前这套环境里，cdp 更合适，不建议现在换。** 三条硬理由：

1. **兼容性有真实风险**：宿主是 `0.2.1-rc.2`，plus 的 peer 范围按严格 semver 不覆盖 prerelease 的 `.1` 位；它自己也没写 `engines.dsh` 护栏，装上去不会提前拦住，只会在运行时暴露。
2. **会丢掉你现在最值钱的两样能力**：从真实 Chrome 导登录（刚验证过能跨重启保留）、任意 heredoc 脚本。
3. **200MB Electron + 独立 Chromium**，为了 UI 换掉一条刚刚修好的链路，性价比不高。

**但 plus 的 UI 确实是代差级的**。如果你后面主要用浏览器做「UI 验收 + 多任务并行」，它值得试。试的方式（可回滚，不破坏现在）：

```yaml
# 1) 先在 cordis.patch.yml 里把 cdp 停掉（避免两套浏览器同时跑）
- id: dsh-browser-cdp
  disabled: true
# 2) 装 plus，重启 dsh
#    dsh plugin --profile desktop add dsh-browser-plus   （或走插件市场）
# 3) 不满意：删掉 disabled 那行、卸载 plus，重启即恢复
```

> 注意：plus 的 README 仍写「固定 Electron 42.9.3」，但 `package.json` 实际是 `44.9.3`（0.5.2 为修证书吊销升上去的）——文档滞后，不影响判断，但说明它迭代较快。

## 九、升级到 1.6.0（2026-10-23 08:10）

### 9.1 做了什么

```
plugin_manager remove_bundle dsh-browser-cdp      # pnpm: -1.2.3
plugin_manager install_bundle dsh-browser-cdp@1.6.0   # pnpm: +1 -41，Packages: +1 -41
```

### 9.2 踩到的回归：1.6.0 在 macOS 起不来

## 十、Codex 式「标注修改」能不能做（2026-10-23 08:20）

### 10.1 拆开看：这个功能由两半组成

| 环节 | cdp 1.6.0 现状 | 证据 |

| 人在页面上**指认元素** | ✅ 有：观察窗「点选引用」→ `[CDP-PICKS]` 结构化块进对话草稿（`backendNodeId`/`tag`/`id`/语义描述，多元素自动编号合并） | `lib/client.js` 的 `createPickControl` / `deliverPickToConversation`，README §“指得准” |

### 10.2 缺的那块已有现成插件：`dsh-annotate`

- 版本 `0.1.15`（2026-10-18），`alaliqing/dsh-annotate`，MIT，SLSA provenance，215KB/10 文件。

- **兼容性比 plus 好**：peer 只要求 `@deepseek-ai/cordis ~4.0.4`，本机是 `4.0.5` ✅；`engines.node >=20`。

### 10.3 结论

- **要“Codex 那种标注面板”**：装 `dsh-annotate`（和 cdp 不冲突：一个负责在预览里标注，一个负责真浏览器操作）。
- **只要“指一下让 agent 改”**：不用装东西，cdp 的点选引用已经能做——你在观察窗点元素 + 说一句改什么，我拿到精确目标就能改。
- **没验证的部分**：`dsh-annotate` 没实装；它靠 iframe 预览本地 app，碰上 `X-Frame-Options`/CSP 的站点可能打不开（README 里列了限制，我没读全）。
